## 0. 概要

マイナビの「スカウトボックス（マイナビ転職）」で **スカウト未読/既読 → 「既読」にチェックして検索** すると、
開封されたスカウトの一覧が出ます。この一覧の行をポータルへ送ると、
配信枠（日 × 号機 × 時間帯）の **開封数** が埋まり、スカウト集計の開封率が出るようになります。

| 用途 | メソッド | パス |
|--|--|--|
| 開封数の送信 | POST | `/api/rpa/mynavi/scout-opens` |

- ベースURL（本番）: `https://bizstudio-portal-production.up.railway.app`
- 認証: リクエストヘッダ **`x-rpa-secret: <共有済みの値>`**（既存の `pdf-upload` / `scout-history` と同じ値）
- ボディ: JSON。**PAD がよくやる「JSON を URL エンコードした文字列」でも受け付けます**（ポータル側で両方パースします）
- **全レスポンスで同じキー集合を返します。** 403 でも 400 でも 500 でも同じキーが揃うので、キーの有無で分岐しないでください
- 日時は JST

### 「既読」で絞った件数がそのまま開封数です

実機で確認済みのとおり、**「既読」で絞ると状況欄が「応募済」「辞退」の行も含まれます**。
除外は不要です。出てきた行をそのまま全部送ってください。

## 1. 送信 `POST /api/rpa/mynavi/scout-opens`

### リクエスト

```
POST https://bizstudio-portal-production.up.railway.app/api/rpa/mynavi/scout-opens
x-rpa-secret: <共有済みの値>
Content-Type: application/json
```

```json
{
  "targetDate": "2026-09-14",
  "rows": [
    { "scoutDate": "2026-09-14 19:52", "recruiterName": "上原 千遥" },
    { "scoutDate": "2026-09-14 19:50", "recruiterName": "藤本 なつみ" }
  ]
}
```

| フィールド | 必須 | 説明 |
|--|--|--|
| `targetDate` | ✅ | 「この日のぶんを送っている」という宣言。`YYYY-MM-DD` |
| `rows` | ✅ | 既読だった行の一覧。**0件の配列でも OK**（その日の開封数が全部 0 になります） |
| `rows[].scoutDate` | ✅ | 一覧の「スカウト日」。**日付＋時刻が必要**（時刻が無い行は読み飛ばされます） |
| `rows[].recruiterName` | ✅ | 一覧の「担当者」。ここから号機を判別します |

会員No・件名・状況は **送っても無視します**（個人単位では持たないため）。送らなくて構いません。

### 読み取る時間の窓（重要）

**`targetDate = D` として送る行は、「D-1 の 20:00 〜 D の 19:59」の窓で読んでください。**

理由: ポータルは 20〜23 時のスカウトを **翌日の 8 時枠** として数えます（配信数側と同じルール）。
`D` の 0:00〜23:59 で読むと、D の 20〜23 時ぶんが D+1 の 8 時枠に乗ります。
その後 `targetDate = D+1` を送ると、D+1 自身の 0〜8 時ぶんで 8 時枠が上書きされ、
**先に入れた D の 20〜23 時ぶんが消えます**。

上の窓で読めば全行が D 自身の枠に収まり、この問題は起きません。
（どちらの送り方でも受理はします。翌日枠へ溢れた場合はレスポンスの `updatedDates` に翌日の日付が出ます）

### 毎晩の運用

- **過去 30 日分を、1 日 1 リクエストずつ、数え直して送る**（既読は後から増えるため）
- ポータル側は **上書き** します。同じ内容を何度送っても数字は増えません
- その日の枠で 1 件も該当が無かったものは **0 で上書き** されます（数え直しなので減ることもあります）

## 2. レスポンス

HTTP ステータスは 200 / 400 / 403 / 500 を返しますが、**本文のキー集合は常に同じ**です。

```json
{
  "status": "OK",
  "targetDate": "2026-09-14",
  "received": 5,
  "counted": 5,
  "skipped": 0,
  "unresolved": 0,
  "unresolvedNames": [],
  "noSlot": 0,
  "updatedSlots": 4,
  "updatedDates": ["2026-09-14"],
  "reason": null
}
```

| キー | 型 | 説明 |
|--|--|--|
| `status` | string | `"OK"` / `"PARTIAL"` / `"FORBIDDEN"` |
| `targetDate` | string \| null | 受け取った対象日 |
| `received` | number | 受け取った行数 |
| `counted` | number | 集計に入った行数 |
| `skipped` | number | 読めずに飛ばした行数（スカウト日が無い/壊れている、担当者が空 など） |
| `unresolved` | number | 担当者を号機に解決できなかった行数 |
| `unresolvedNames` | string[] | 解決できなかった担当者名（重複なし） |
| `noSlot` | number | 該当する配信枠が無かった行数（枠は作りません） |
| `updatedSlots` | number | 実際に値が変わった枠の数 |
| `updatedDates` | string[] | 更新した枠の日付一覧 |
| `reason` | string \| null | PARTIAL / エラーの説明。正常時は `null` |

### status の意味

| status | HTTP | いつ | PAD 側の扱い |
|--|--|--|--|
| `OK` | 200 | 全行が正常に集計された | 成功 |
| `PARTIAL` | 200 | 一部の行を飛ばした（`skipped` / `unresolved` / `noSlot` のどれかが 1 以上） | **成功扱いでよい。** ただし `reason` をログに残す |
| `PARTIAL` | 400 | `targetDate` が無い・日付として不正 | リクエストの作りが誤り。要修正 |
| `FORBIDDEN` | 403 | `x-rpa-secret` 不一致 | シークレットを確認 |
| `PARTIAL` | 500 | ポータル側の予期しないエラー | リトライ可。LINE WORKS に自動通知が飛びます |

`unresolvedNames` に名前が出続ける場合は、担当者マスタ（`/scout/masters`）への登録が必要です。ポータル側担当へ連絡してください。

## 4. 時間帯の数え方（ポータル側の処理・参考）

送られた各行は、スカウト日の「時」から配信枠へ振り分けられます。
**配信数（分母）と同じルール**です。PAD 側で畳み込む必要はありません。そのままの時刻を送ってください。

| スカウト時刻（JST） | 乗る枠 |
|--|--|
| 0〜7 時 | **その日の 8 時枠**（早朝送信は 8 時枠へ畳み込み） |
| 8〜19 時 | その時間の枠（1:1） |
| 20〜23 時 | **翌日の 8 時枠** |

配信枠は 8〜19 時の 12 枠しかありません。

## 5. 動作確認用のサンプル

```bash
curl -X POST "https://bizstudio-portal-production.up.railway.app/api/rpa/mynavi/scout-opens" \
  -H "x-rpa-secret: <共有済みの値>" \
  -H "Content-Type: application/json" \
  --data-binary @body.json
```

`body.json`（UTF-8 で保存すること）:

```json
{
  "targetDate": "2026-09-14",
  "rows": [
    { "scoutDate": "2026-09-14 08:15", "recruiterName": "藤本 なつみ" },
    { "scoutDate": "2026-09-14 09:30", "recruiterName": "藤本 なつみ" },
    { "scoutDate": "2026-09-14 19:52", "recruiterName": "上原 千遥" }
  ]
}
```

結果はポータルの **スカウト集計 → 配信枠管理（`/scout/slots`）** の「開封数」「開封率」列で確認できます。

## 6. 既知の制限

- **社員枠（手動配信）は「配信枠管理」の一覧には開封数が出ますが、スカウト集計のグラフ・表には出ません。**
  社員の枠は集計対象フラグ（`isAggregationTarget`）が false のためです。
  「藤本 夏海 の手動配信も集計に含める」を集計画面側でも効かせるかどうかは、
  配信数の集計にも影響するため業務側の判断待ちです。
- 開封数だけを入れても、その枠に配信数が入っていなければ開封率は出ません（`-` 表示）。
