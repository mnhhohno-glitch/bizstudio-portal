### 0-1. 最重要発見: 「幅のある評価」はAIの暴走ではなく、**こちらがそう指示している**

```
| 希望 × 通過 | 総合評価 |
| A × A       | 総合A     |
| A × B       | 総合A〜B  |  ← 幅
| B × A       | 総合A〜B  |  ← 幅
```

### 1-2. 特に見落としやすい箇所トップ5

1. **`HistoryTab.tsx` L886/890 の行末 `$` アンカー** — `[ABCD]?\s*$` は `B+` にマッチせず、既存行を検出できないまま**新しい行を挿入**して評価行が2重化する。`[ABCD]` の機械置換では見落としやすい形（`?` 付き＋`$`）。
2. **`comment-split.ts` L17 の「+ だけ残る」漏洩** — 除去系は動いているように見えて壊れる。残った `+` が求職者向けコメント冒頭に出る。
3. **`toMatchLabel()` が3ファイルに完全コピー** — `default: return ""` に落ちるため例外もログも出ず、1箇所だけ直すと「個別編集では出るが一括同期では消える」再現困難な不具合になる。
4. **AI側を直さないと5段階は永久に発火せず、しかもテストで気付けない** — 既存データは全部 A/B/C/D なので全テストが通る。加えて `load-job-matching-skill.ts` のモジュールキャッシュにより **SKILL.md 変更はプロセス再起動まで反映されない**（staging で「直したのに効かない」に見える）。
5. **幅評価の握りつぶしと B+ 対応の相互作用** — SKILL.md を直さないまま `(B\+|[ABCD])` だけ入れると `B+〜C` が生まれ、`hasValidThreeAxisMarkers` は前方一致で**通ってしまうため破損検知にも掛からず** B に潰れ続ける。

## 4. 調査項目4: 集計を出す対象範囲（推奨案）

### 4-1. 前提として判明した構造

| 項目 | 内容 |
|--|--|
| `files`（L743） | `GET /files?category=BOOKMARK` の結果。**`archived` 未指定＝紹介保留は含まない**（API L56-62 が既定で `archivedAt: null`） |
| `filteredFiles`（L1066-1076） | `files` に**検索キーワード**（ファイル名部分一致）と**日付**（`createdAt` 完全一致）を適用し、ソートしたもの |
| 紹介保留 | `ArchivedBookmarkSection`（L2087-2573）が**完全に独立**した state / fetch で管理 |
| サイト経由PDF無し行 | L1553-1554 で `origin==="candidate" && !driveFileId && !aiAnalysisComment` は「**AI評価対象外**」と表示され、3軸バッジを描画しない |
| 件数バッジ | サブタブの件数は `files.length`（フィルタ**前**） |
| 全選択・一括操作・一覧描画 | すべて `filteredFiles`（フィルタ**後**） |

### 4-2. 推奨案: **`filteredFiles` ベース（絞り込み後）＋ 絞り込み中の明示**

理由:

1. **一覧との整合が最優先。** 画面に見えている行と数字が一致しないと、CA は必ず「どの数字を見ているか」で混乱する。全選択・一括操作もすべて `filteredFiles` 基準なので、集計だけ `files` にすると**この画面で唯一フィルタを無視する要素**になる。
2. **「引き当てた後の選定率」という目的に合う。** 日付で絞れば「その日の引き当ての質」、検索で絞れば「特定媒体の質」が見える。母数固定より用途が広い。
3. **実装コスト差はほぼゼロ。** どちらも同一スコープに存在する配列を `reduce` するだけ。`useMemo` で足りる。

ただし**誤読リスクへの対処を必須条件とする**:

- `searchQuery` または `filterDate` が有効なとき、集計エリアに **「絞り込み中（N件 / 全M件）」を明示**する
- 絞り込み解除ボタンを集計エリア内に置く

### 4-3. 母数から除外すべき行

| 対象 | 判断 | 理由 |
|--|--|--|
| **サイト経由PDF無し**（AI評価対象外） | **除外** | 一覧で「AI評価対象外」と明示されている行を母数に入れると選定率が不当に下がる |
| **評価なし**（コメントNULL・マーカー無し） | **別枠表示**（「未評価 N件」） | 分母に入れるか否かで数字が変わる。隠さず別枠で出す |
| **紹介保留** | **含めない**（ただし §4-4 参照） | `files` に含まれず、別サブタブで独立管理されているため |

### 4-4. ★用語の衝突（要判断）

日報側に**同名の「選定率」が既に存在する**。

| | 日報の選定率 | 今回ブックマークタブに出す指標 |
|--|--|--|
| 定義 | **出力数 ÷ (BM数 + 紹介保留数)** | 総合評価の内訳（A/B+/B/C/D の構成比） |
| 出典 | `dailyReport/jobSearch.ts` L5-12（T-092 で変更） | 新規 |
| 紹介保留 | **含む** | 含まない |
| 評価ランク | **参照しない** | 参照する |

**まったく別物である。** 同じ「選定率」という語を使うと、日報とブックマークタブで違う数字が並ぶ。

**推奨**: ブックマークタブ側は「選定率」という語を使わず、**「評価内訳」「引き当ての質」**等の別名にする。あるいは「良評価率（A+B+ の割合）」のように定義を明示した名前にする。

なお `.claude/03-portal-spec.md` L169 と `14-ui-component-map.md` L1094 には**T-092 前の旧定義 `(A+B+C)÷合計BM` が残存**しており、B+ 追加時に分子の列挙が問題化する。併せて更新が必要。

## 6. Phase 2 実装で踏みそうな地雷

1. **AI側を直さないと何も起きない。しかもテストは全部通る。** 既存データは全て A/B/C/D なので、コード側だけ5段階にしても既存テストは緑のまま。B+ が1件も生成されないことに気付くのはリリース後。
2. **SKILL.md のモジュールキャッシュ。** `load-job-matching-skill.ts` の `cachedSkill` はプロセス再起動まで保持。staging で「直したのに反映されない」に見える。**再デプロイ必須。**
3. **`+` は正規表現メタ文字。** `B\+` のエスケープ漏れが全パース箇所で起こりうる。
4. **`[ABCD]` → `(B\+|[ABCD])` の交替順序。** `([ABCD]\+?)` だと `A+` / `C+` まで拾ってしまう。**B+ を先に試す交替**が安全。
5. **行末 `$` アンカー付きの正規表現**（HistoryTab L886/890/895）は機械置換では直らない。個別対応が必要。
6. **`toMatchLabel()` の3重コピー。** 1箇所だけ直すと一括同期でだけ壊れる。**共通化を同時に行うのが安全。**
7. **`DailyReportView.tsx` の同名定数の取り違え。** L96 `RANK_ORDER`（求職者ランク・**触るな**）と L104 `RATING_ORDER`（AI評価・**直す**）が同一ファイルに同居。
8. **過去データと新規データの混在。** 過去は A/B/C/D のみ、7/17〜は幅混在、B+ 導入後は5段階。**3世代が同一カラムに混在**する。集計の見せ方に注釈が必須。
9. **幅評価146件の後始末。** 再判定しない方針なので、`■ 総合：B〜C` の行は残る。パーサが先頭1文字を拾う限り B と表示されるが、**B+ 対応でパーサを触るときに挙動が変わらないよう固定**すること（`B〜C` が誤って `B+` にならないか）。
10. **mypage / kyuujinPDF 側の A/B/C/D 前提分岐。** portal は `aiMatchRating` を生値パススルーしている。下流に switch があれば別リポジトリで落ちる。**要確認。**
11. **`hasValidThreeAxisMarkers` のクライアント/サーバ二重定義。** 片側だけ直すと invalid-only 再解析の対象件数がズレる（コード内コメントで明示的に警告されている既知の罠）。
12. **AI評価はコスト律速。** 全件再判定はしない方針だが、`invalid-only` 判定を厳しくし過ぎると B+ 付き正常レコードを「破損」と誤認して大量再解析が走り、コストが跳ねる。
