### ユーザー検索が使えなかった件

`GET /users` は **403 `Authorization_RequestDenied`（Insufficient privileges）** を返した。付与済みの権限が `Files.ReadWrite.All` のみで、ディレクトリ読み取り（`User.Read.All`）が無いため。

## 3. Step 4 文字コードの検証結果（最重要）

### 3-1. 検証方法

Phase 1 で懸念していた特殊文字を含む本番パスに対し、**ライブラリのフォールバックを通さず生 `fetch` で1方式・1回だけ**叩いて成否を確かめた。多段フォールバックを通すと「NFD でも OK」と出てしまい、どの方式が実際に通ったのか判別できないため。

### 3-2. 結果

#### ケースA: 全角チルダ `～`(U+FF5E) 入り
`/ビズスタジオ/6.求職者書類関連/4.安藤/2024～/2024年/5001272末富温`

| 送った方式 | DB値との異同 | 結果 |
|--|--|--|
| そのまま（DB値） | ＝同一 | **200 OK** `name="5001272末富温"` |
| NFC | ＝同一 | **200 OK** |
| NFD | ≠ | **200 OK** |
| NFKC | ≠ | **404 `itemNotFound`** |

#### ケースB: 異体字 `﨑`(U+FA11) 入り
`/ビズスタジオ/6.求職者書類関連/1.大野/2024/202409/5001072_松﨑 優真`

| 送った方式 | DB値との異同 | 結果 |
|--|--|--|
| そのまま（DB値） | ＝同一 | **200 OK** `name="5001072_松﨑 優真"` |
| NFC | ＝同一 | **200 OK** |
| NFD | ≠ | **200 OK** |
| NFKC | ＝同一 | **200 OK** |

#### ケースC: 全角スペース `　`(U+3000) 入り
`/ビズスタジオ/6.求職者書類関連/4.安藤/2024～/2024年/24年11月/5001318石谷　安代`

| 送った方式 | DB値との異同 | 結果 |
|--|--|--|
| そのまま（DB値） | ＝同一 | **200 OK** `name="5001318石谷　安代"` |
| NFC | ＝同一 | **200 OK** |
| NFD | ≠ | **200 OK** |
| NFKC | ≠ | **404 `itemNotFound`** |

#### 対照: 存在しないパス
`/ビズスタジオ/6.求職者書類関連/1.大野/2024/202409/存在しないフォルダ_XYZ` → **404 `itemNotFound`**

### 3-3. 結論

1. **DB が保持する文字列はすでに NFC。**`s === s.normalize("NFC")` が全ケースで成立した。
2. **Graph 側がパス照合時に正規化を吸収する。**NFD にして送っても 200 が返り、レスポンスの `name` は元と**同一のコードポイント**で戻る（`﨑` は U+FA11 のまま、全角スペースは U+3000 のまま）。
3. **NFKC をかけると壊れる。**`～`(U+FF5E)→`~`(U+007E)、全角スペース→半角に変換され 404 になる。
4. したがって **正規化フォールバックは1件も救わない**。むしろ「フォルダが本当に無い」という最も多いケース（404件）で API 往復が方式数ぶん増えるだけ。

### 3-4. 成功した方式と、ライブラリへの反映

**成功した方式 = 「DB の値をそのまま送る」**。

これを受けて `src/lib/microsoft-graph.ts` から多段フォールバックを削除し、次の形にした。

```ts
/**
 * ★ Unicode 正規化はかけない（T-159 Phase 2-0 で実測して確定）。
 *   - DB が保持する文字列は既に NFC
 *   - Graph 側がパス照合時に正規化を吸収する。NFD にして送っても 200 が返る
 *   - **NFKC をかけると壊れる**。～(U+FF5E)→~(U+007E)、全角スペース→半角 に変換され 404 になる
 * 正規化フォールバックは Graph 側が吸収する以上1件も救えず、逆に「フォルダが本当に無い」という
 * 最も多いケースで API 往復が方式数ぶん増えるだけなので置かない。
 * 将来この層でパスを加工したくなったら、NFKC / toLowerCase / trim を挟まないこと。
 */
export function assertPathUnmodified(path: string): string {
  return path;
}
```

**これにより 404 `itemNotFound` は「本当に存在しない」を意味すると断定できる**ようになった。Phase 1 で挙げた「404 が文字コード差なのかフォルダ不在なのか区別できない」という懸念は解消。

パスのエンコードはセグメント単位の `encodeURIComponent`（`/` は区切りとして残す）で全件通っている。

## 10. 気づいた懸念点

### 10-1. ★ 大野氏のドライブ残量は 876GB。当面は問題ないが監視は要る

`used 141.14GB / total 1024.00GB`。Phase 1 で見積もった流量は月あたり約1,689件・平均 280KB 程度なので**月およそ 0.5GB**。単純計算で1,700か月ぶんの余裕があり、**容量が近い将来の制約になることはない。**

ただし OneDrive にはこれとは別に**アイテム数**の実用上限（1ライブラリ 30万アイテム推奨、同期クライアントの性能劣化はもっと手前）がある。既に 6.求職者書類関連 配下だけで相当数あるはずで、**年間2万件のペースでファイルが増えることの累積影響は Phase 2-b 稼働後に観測すべき。**

### 10-2. ★ `Files.ReadWrite.All` はテナント全体権限のまま（Phase 1 からの継続）

今回 `GET /users` が 403 になったことで、**この資格情報がディレクトリを読めないことは確認できた**（`Files.ReadWrite.All` のみ）。それでも「テナント内の全ユーザーの OneDrive と全 SharePoint サイトに読み書きできる」ことは変わらない。

`MS_GRAPH_CLIENT_SECRET` は Railway の環境変数として保持しており、Railway の権限を持つ者は参照できる。**同期ロジック側で書き込み先パスを `/ビズスタジオ/6.求職者書類関連/` 配下にハードコードで限定するガードを Phase 2-a に必ず入れること。**（実データ1734件は全件このプレフィックスに合致することを本調査で確認済み。）

### 10-3. ★ シークレットの有効期限が「静かに壊れる」最大要因のまま

期限切れ時のトークン取得失敗は `AADSTS7000222` として `getGraphToken()` が throw するが、同期は fire-and-forget で隔離されるため **portal のアップロードは成功し続ける**。CA からは正常に見えたまま OneDrive にだけ入らなくなる。

Phase 2-b で `GIVEN_UP` / `FAILED` の急増を検知する導線を必ず用意すること。**有効期限をカレンダーに登録しておくことも併せて推奨。**

### 10-4. `5.面接対策` `6.面談` は雛形の世代差で半数しかない

`1.原本`〜`4.応募企業` が約1,320件あるのに対し、`5.面接対策` 625件・`6.面談` 609件。雛形が途中で拡張されたことが窺える。

本件（`2.求人` / `3.BS作成書類`）には影響しないが、**将来 MEETING カテゴリを `6.面談` へコピーする案が出た場合、実在率は半分程度になる**ことを見込んでおく必要がある。

### 10-5. `BEFORE` の求職者にファイルが発生したときだけスキップが出る

実在率100%だったのは `ACTIVE` / `ENDED` / `WAITING` と「直近30日に動きがあった88人」。一方 `BEFORE` は1,436人中404人がフォルダ無しで、母数としては最大の集団。

`BEFORE` の求職者に BOOKMARK が付くこと自体は起こりうる（初回提案の直前など）。その場合は `SKIPPED_NO_SUBFOLDER` が出る。**「フォルダを作らない」は確定仕様なので正しい挙動だが、CA から見ると「新しく担当した人の求人票が OneDrive に入らない」形で現れる。**Phase 1 で設計した CA 向けバッジ表示は、この経路のために必要。

### 10-6. 表記ゆれ34種は吸収しないと決めたが、記録は残すべき

`SKIPPED_NO_SUBFOLDER` を記録する際、**その求職者フォルダの子フォルダ名一覧を `errorMessage` に添えておく**と、CA が「どのフォルダに手で入れればいいか」を即座に判断できる。追加コストはほぼゼロ（子一覧はフォルダ存在確認のついでに取れる）。Phase 2-a の実装時に入れることを推奨。

### 10-7. 429 は今回1件も出なかったが、油断はできない

1,734リクエストを並列5で流して 429 ゼロ。ただしこれは GET 中心の負荷。**書き込み（PUT / createUploadSession）は Graph 側のコストが重く、制限に当たりやすい。**実装済みの `Retry-After` 尊重＋指数バックオフはそのまま維持すること。

### 10-8. `src/lib/microsoft-graph.ts` は接続層のみで、まだどこからも呼ばれていない

本コミット時点でこのファイルを import している本番コードは無い。**デプロイしても挙動は一切変わらない**（純粋追加）。`07-deploy-rules.md` の「純粋追加機能 → master 直 push 可」に該当する。
