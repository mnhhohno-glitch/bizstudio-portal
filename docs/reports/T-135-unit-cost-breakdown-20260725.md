## Step 2. キャッシュ入力が入力の3.76倍ある理由

### 何をキャッシュしているか（コード確認済み）

`gemini-cache.ts` + `gemini-structurer.ts` の実装:

1. **固定部（毎回不変）**: 抽出ルール指示文 + JSON スキーマ定義 + 職種マスタ + 業種マスタ + エリアマスタ
   - `buildPrompt(masters)` の出力 ≈ 43,000文字 / **≈ 8,197 トークン**
   - `gemini-cache.ts` が Gemini Context Cache（Google サーバー側）に TTL 3600秒で保持
   - `displayName`（固定部の sha256）で全 invocation が共有（バッチ初回に1回 create、以降は参照のみ）

2. **可変部（PDF本文のみ送信）**: 各求人票のテキスト
   - キャッシュ利用時: 可変部のみ送信（≈ 2,177 tok/件 = input の全量）
   - キャッシュ非利用時: 固定部 + 可変部の全文送信（≈ 10,374 tok/件）

### キャッシュの単価比較

| 送り方 | トークン | 単価 (¥/1M) | 日額 (¥) |
|--|--|--|--|
| **キャッシュ入力として送信（現状）** | 7,385,497 | 4.8 | **¥35.45** |
| 通常入力として送信（キャッシュなし想定） | 同上 | 48 | ¥354.50 |

**キャッシュによる節約: ¥319/日 = ¥9,572/月**（90%割引）。

### 判定: **「良い節約」**

- キャッシュが多い（3.76倍）のは、固定部（マスタ3種 + 指示文 + スキーマ）が1件あたり 8,197 tok と大きいため。これは構造化精度を保つために必要な情報量
- キャッシュ入力の日額は ¥35（構成比 1.4%）。仮に固定文を半分に圧縮しても、節約は ¥18/日 = ¥525/月にしかならない
- 固定文の短縮は **コスト削減効果が極めて小さく、精度劣化リスクのみが残る**ため非推奨

### 固定文が肥大している兆候はあるか

プロンプト（`buildPrompt()` / `gemini-structurer.ts:186-303`）を通読した結果:
- few-shot 例は含まれていない（ルール記述のみ）
- 使っていない例文・冗長な指示は見当たらない
- マスタは `groupHierarchy()` で「大 > 中: 小1、小2、…」に圧縮済み（1行/中分類。トークン節約の工夫あり）
- **肥大の兆候なし**。8,197 tok は「職種・業種・エリアの3階層マスタ + 30フィールドの抽出ルール」としては妥当

## Step 3. thinking が出力の1.99倍ある理由

### thinkingConfig の設定状況（コード確認済み）

| ファイル | 処理 | モデル | thinkingConfig |
|--|--|--|--|
| `gemini-structurer.ts:474-479` | **job-structuring** | gemini-2.5-flash | **設定なし（デフォルト＝無制限）** |
| `company-name.ts:52` | company-name-normalize | gemini-2.5-flash-lite | `thinkingBudget: 0`（無効） |
| `ai-detail.ts:189` | ai-detail | gemini-2.5-flash-lite | `thinkingBudget: 0`（無効） |
| `company-summary.ts:95` | company-summary | gemini-2.5-flash-lite | 設定なし |

**job-structuring のみ thinking が無制限で走っている。** company-name と ai-detail は意図的に無効化済み。

### この処理に thinking は必要か

job-structuring の処理内容:
1. PDF テキストから source_job_id を抽出（パターンマッチ）
2. 30+ フィールドの情報抽出（JSON 構造化）
3. 職種・業種・エリアの3階層マスタに分類（最も判断を要する）
4. source_texts の逐語転記（機械的コピー）
5. confidence の self-report

**判定: 構造化の大部分は「情報の抜き出し＋転写」であり、深い推論は不要。** ただし職種分類（階層マスタから最適な小分類を選ぶ）には一定の判断が必要で、thinking を完全に無くすと分類精度が落ちるリスクがある。

### 実測: thinking トークンの分布

1件あたり平均:
- thinking: **4,570 tok**（最小〜最大は後述の7/24検証で確認可能）
- output: **2,290 tok**
- ratio: **1.99x**

出力 2,290 tok に対して思考 4,570 tok は、情報抽出タスクとしては**過剰な可能性が高い**。比較参考: portal の file-parse（同じく情報抽出だが gemini-3-flash-preview）では ratio = 1.89x。

### 実績データの裏付け

`ai_usage_logs` の全期間データで、job-platform からの記録は **job-structuring のみ**（他3処理のレコード: 0件）。

考えられる理由:
- company-summary / company-name / ai-detail はいずれも**DB キャッシュ済み**（会社単位 or 求人単位で1回生成・以降は列読み）。大半の呼び出しはキャッシュヒットで AI を呼ばない
- 新規会社・未生成求人の頻度が低い（月数十件レベル）
- 3処理とも gemini-2.5-flash-**lite**（入力 $0.10 / 出力 $0.40 = 2.5-flash の 1/6 単価）

### 各処理を止めた場合に失われるもの

| 処理 | 止めた場合の影響 |
|--|--|
| job-structuring | **停止不可**。求人データの構造化自体が止まる |
| company-summary | マイページの「この会社について」欄が空になる。検索・マッチングには影響なし |
| company-name-normalize | 会社名にキャッチコピー（「★東証プライム★」等）が残る。検索精度にはわずかに影響（突合精度） |
| ai-detail | マイページの「この求人について詳しく知る」が空になる。検索には影響なし |

**結論: 2-4 の停止は月 ¥30 未満の節約にしかならず、停止する意味がない。** コスト削減は job-structuring の thinking に集中すべき。

## 想定と違った点

1. **キャッシュは「無駄」ではなく「良い節約」だった。** キャッシュ入力 738万 tok は入力の 3.76 倍だが、通常入力より 90% 安い単価（¥4.8 vs ¥48/1M tok）で送られており、¥319/日 = ¥9,572/月を節約している。キャッシュが多い＝無駄、ではない

2. **job-platform の4処理中、コストに意味があるのは job-structuring のみ。** 残り3処理は gemini-2.5-flash-lite（6倍安い）+ DB キャッシュ（1回生成・以降は読むだけ）で月 ¥30 未満。停止の検討自体が不要

3. **thinking が「出力の2倍」は、比率としてはそこまで極端ではない。** portal の file-parse（gemini-3-flash-preview）でも ratio = 1.89x。ただし job-structuring は呼出量が圧倒的に多い（450件/日 vs portal 30件/日）ため、絶対額で支配的になっている

4. **thinking 計装前（旧記録値 ¥449/日）と真の月額（¥1,371/日）の乖離は 3.05 倍。** 先行調査の推定 3.4 倍（T-131 backfill ベース）は概ね的中していた
