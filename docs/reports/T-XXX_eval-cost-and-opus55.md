### 1-2. 使い回し（キャッシュ）の効き方

**印の位置と並び**（`src/lib/analyze-batch-cache.ts`）: system が ①固定部（1時間）→ ②候補者情報（5分）→ ③バッチ指示（印なし）の順。user に ④求人票（印なし）を置く。共通部分は先頭にあり、1時間の印が5分の印より前という API の制約も満たしている。②は run 内で同じ文字列になるよう、`sessionId` 単位で30分保持している（`runContextCache`）。

**実際の効き方（ログ）**:

### 1-3. 評価のやり直し

ログには評価した求人の ID が無い。そこで各 run（候補者ごとに batchIndex 0 から続く呼び出し）について、本番の選び方で対象を復元した。本番の選び方は「未アーカイブ・`extractedText` あり・`createdAt` の新しい順に先頭から5件ずつ」。全件分析も追加分析も、新しい順の先頭 N 件（N = その run の評価件数）になる。**2,940件中 2,105件（71.6%）を求人単位まで復元できた。** 未評価/破損のみの再実行（332件）と検証の呼び出し（306件）は対象が決まらないため除いた。

| 追加分析（新しく増えた分のみ） | 195 | 1,232 | ¥11,823 |
| 全件分析 | 47 | 758 | ¥5,738 |
| 検証の呼び出し（8/28） | 86 | 306 | ¥4,086 |

| 復元できず（その後削除された等） | 8 | 197 | ¥1,550 |
| 途中で止まった run | 10 | 115 | ¥869 |

| やり直し（復元できた 2,105件の中） | 回数 | 費用 | 30日換算（復元率で割り戻し） |
|--|--:|--:|--:|
| 同じ求職者×同じ求人の2回目以降の評価（131求人） | 160回 | ¥1,669 | ¥2,331 |
| うち入力が変わっていない（指示の定義: 求人本文・書類・面談ログ要約・CAメモ・面談ガイドに更新なし） | **158回** | **¥1,642** | **¥2,293** |
| うち入力が変わっていない（厳しめ: 上記＋応募履歴・ブックマーク一覧も不変） | **59回** | **¥432** | **¥603** |

- 変わった理由（厳しめ・重複あり）: ブックマーク一覧 100・応募履歴 33・書類 2・面談ログ要約 2。候補者情報には「アップロード済みファイル」一覧（ブックマークのファイル名を含む）と応募履歴が入る。このため、ブックマークを1件足すだけで、送信内容としては「変わった」ことになる。ただし評価への影響は小さいと考えられる。
- **やり直しが起きる経路（コードから特定）**
  1. **「全件分析」ボタン**（`handleFullAnalysis`）は、評価済みかどうかを見ずに、未アーカイブの全ブックマークを毎回評価し直す。「未評価/破損のみ」トグルが ON のときだけ未評価・破損に絞る。
  2. **途中で止まった run の押し直し**: 最終バッチまで届かずに止まった run の直後10分以内に、同じ候補者でもう一度押した例が **28回**（止まった側の費用 ¥1,585）。押し直すとバッチ1から全部やり直しになる。止まる原因はログからは分からない。サーバー側は失敗ログ0件なので、画面側の中断（パネルを閉じた・通信切れ等）と考えられる。
  3. **「追加分析」の基準日**（`handleAdditionalAnalysis`）: 最後の「【求人分析」チャットの時刻を基準に、それより後に作られたブックマークを対象にする。完了カードは最終バッチでしか書かれないため、途中で止まった run の後の追加分析は、1つ前の完了時刻を基準にして、評価済みの分まで再評価する。
  4. **「未評価/破損のみ」**: 形式崩れ（3軸が欠けた出力）の再実行。332件・¥2,967。これは必要なやり直し。

## 第4部 まとめ（試算・月額）

基準: 手動評価の直近30日は ¥27,033。うち ¥4,086 は 8/28 の検証の呼び出しで、**CA の通常利用は 約¥22,950/月**。削減額はこの通常利用に対する見込み。

| 手 | 月額の削減見込み | 待ち時間への影響 | 質への影響 |
|--|--:|--|--|
| Opus 5.5 に切り替え（effort low） | **約 −¥4,600（−20%）** | **短くなる**（1バッチ 100秒 → 60秒） | **目安未達**（一致 48.0%・取りこぼし 4.0%・通過率が厳しめ）。本番の応答読み取り箇所の修正が必須 |
| 使い回し S1（固定部の想定外の書込をなくす） | 約 −¥250 | なし | なし |
| 使い回し S2（S1＋候補者情報を1回目で書込・残り読込） | 約 −¥500 | **増えない**（現行がすでに逐次送信） | なし |
| 入力が変わらないやり直しを止める | **約 −¥600（厳しめ）〜 −¥2,300（指示の定義）** | **短くなる**（再評価が減る分） | なし（同じ入力の再評価をしないだけ。Opus 自身のブレによるランクの揺れも減る） |
| 組み合わせ（やり直し停止〔指示の定義〕＋S2） | 約 −¥2,700（−12%） | 短くなる | なし |
| 組み合わせ＋Opus 5.5 | 約 −¥6,700（−29%） | 短くなる | Opus 5.5 の目安未達がそのまま残る |

**推奨する順番**
1. **入力が変わらないやり直しを止める。** 質を変えずに下げられる唯一の手。候補は2つある。
   - 「全件分析」で、評価済みで、評価後に入力（求人本文・書類・面談ログ要約・CAメモ・面談ガイド）が変わっていない求人を飛ばす。
   - 途中で止まった run を押し直したときは、続きから再開する。
   - 何を「変わった」とみなすか（応募履歴やブックマーク一覧の変化を含めるか）で、効果が ¥600〜¥2,300 と変わる。ここは将幸さんの判断。
2. **使い回しの改善は見送り。** すでに効いていて、伸びしろは月 ¥250〜¥500。手を入れる価値は小さい。
3. **Opus 5.5 は今は切り替えない。** 速さ（−40%）と費用（−20%）の利点は大きいが、通過率の付け方が Opus 4.6 と系統的に違う。再挑戦するなら、既定の effort `medium` で同じ100件を試すのが次の一手（見積もり ¥500〜¥700）。
4. 評価費用の半分は出力。検証の呼び出し（8/28 の ¥4,086）のような一時的な大量評価は、Batch API（半額）で回すと安い。
