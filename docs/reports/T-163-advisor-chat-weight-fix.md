### C2: チャット長文 vs 行コメントの内容一致【実測・無作為10本を目視比較】

- 行コメントは「【会社名】タイトル行 + 3軸マーカー + ◆おすすめポイント（本人向け）+ ◆選考分析（CA向け）」を**チャット本文の該当求人の記述と同等の情報量**で保持（例: 竹下さん・松澤さんの各求人で全項目一致を確認）。
- チャットにしかないのは (a)「候補者サマリー」= 候補者contextの再掲（求人固有情報ではない）、(b)「総合まとめ（総合優先順位）」= **完了カードに残す設計のため欠落しない**。

**分岐判定: C1 欠損 0.38% < 5% かつ C2 で該当求人の記述の欠落なし → §3 のすべてを実装（フルスコープ）。**

## 5. §4 連続コール間隔の集計と 1時間TTL化の可否判断【実測】

`advisor_usage_logs` の `endpoint='advisor-chat'`、同一 candidate_id の連続コール間隔（187ペア）:

| 窓 | 割合 |
|--|--|
| 5分以内 | **37.4%**（調査報告書の 37.4% と一致 = 検算OK） |
| 15分以内 | 48.1% |
| 30分以内 | 51.9% |
| **60分以内** | **54.0%** |

判断基準: 書き込み単価は 5分TTL=1.25倍・1時間TTL=2倍・読み込み=0.1倍。Sonnet 入力 $3/MTok・固定ブロック 23,852トークンで、
1時間TTLが「キャッシュ無し」より得になるのはヒット率 **52.6%超**、「現状の5分TTL（実測ヒット29.6%)」より得になるのは **57.5%超**。

**→ 60分以内の割合 54.0% < 57.5% のため、1時間TTL化は見送りが正しい。**（52.6%は僅かに超えるが、比較対象は現状の5分TTLなので 57.5% が基準。TTL変更は今回実施していない）

## 8. 実装上の設計判断（プロンプトからの逸脱があり得る点の明示）

**総合まとめの入力供給元の変更**: 従来、最終バッチの総合まとめは「チャット履歴に書き込まれた過去バッチ結果」を読み戻して生成していた（旧 route.ts:631-638）。中間バッチのチャット書き込みを廃止すると総合まとめの入力が消えるため、供給元を **analyze-batch 内のプロセス内キャッシュ（`runBatchResultsCache`）** に変更し、プロセス再起動時は `candidate_files.aiAnalysisComment` から再構成するフォールバックを付けた。

- **system プロンプト本文・モデル・max_tokens・バッチ分割は不変。** 渡す内容は従来と同じ `compressBatchResultForSummary` 圧縮形式（会社名+3軸のみ）で、入力サイズは従来同等以下。
- 本番検証で総合まとめが全バッチの求人を網羅することを確認済み（§6-2）。

**完了カードの母数**: カードの件数集計は「その求職者の現在の分析対象ブックマーク全件（`allBookmarks`）」を母数にした。通常の「全件分析」ではこれは run の対象と一致し、かつ一覧の内訳パネルの母数とも一致する。「追加のみ」分析では母数が追加分のみになる（run 内整合は保たれる）。
