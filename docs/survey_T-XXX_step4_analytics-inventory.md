## 1. 結論

1. **第1段（今あるデータ・集計値のみ・秘密URLのままで可）で出せる主なもの**: 進行中の案件の今の数（選考中・承諾済みで未入社・今後の面談予定）、初回面談の月ごとに同じ求職者群を追ったつながり（提案→応募→書類通過→企業面接→内定→承諾の人数と日数。実データで出せることを確認した・§3-7）、承諾売上・粗利の CA別・月別と単価の分布、期間ユニーク人数、希望職種・現年収帯・転職時期別の切り口（初回面談の構造化項目の入力率は約93%）、データ品質の警告。
2. **記録が無く、今から記録を始める必要がある主なもの**: 選考ステータスの変更日（辞退・見送りの日付）、**進行中案件の日次スナップショット**（予測の答え合わせ用・過去分は作れない）、支援状況（活動中・終了）の変更履歴、売上の確定/見込・取消・返金、CA の在籍期間（入社日は CA 8名中3名だけ入っている）、「転職活動」の単位（今は1人1レコード）。
3. **OAuth が必要になる境目**: 「求職者1人・案件1件ごとの行」を返すかどうか。人数・件数・割合・日数の分布（少人数は伏せる）までは秘密URLのまま出せる。1行1求職者の明細（匿名化しても）を外に出すなら、先に OAuth とポータルのログインの強化（今の `bs_session` はユーザーIDそのまま）が必要。
4. CA の在籍情報に要件書と合わない点がある（§3-2）: **「橋田」さんは社員マスタに見当たらない**（8月に担当を持ち始めた CA は藤田 愛さん 1000028）。南條さん・岡田さんが CA・在籍として登録されているが要件書の一覧に無い。
5. 優先順位は「予測売上に要る材料（進行中案件・段階ごとの承諾率と日数・単価と取消）」→「CA の在籍期間」→「同じ求職者群を追った活動の分析」→「切り口」の順（§5）。

## 5. 段階的な実装案（提案のみ）

## 6. OAuth 切り替えの最小構成案

### 6-1. ChatGPT の MCP アプリが求める OAuth（要確認）

MCP の認可仕様（2025-06-18 版）と、ChatGPT のアプリ連携の一般的な条件として知られているもの。**実装前に OpenAI の最新の開発者向け資料で確認すること**（今回は外部資料を読んでいない）。

- OAuth 2.1・認可コードフロー＋PKCE（S256）
- MCP サーバーが「保護されたリソースのメタデータ」（`/.well-known/oauth-protected-resource`・RFC 9728）を返し、401 の `WWW-Authenticate` で場所を知らせる
- 認可サーバーのメタデータ（`/.well-known/oauth-authorization-server`・RFC 8414）
- クライアントの動的登録（RFC 7591）か、それに代わる方式（クライアントIDのメタデータ文書）への対応
- アクセストークンは `Authorization: Bearer` ヘッダで届く → **URL にも Railway の HTTP ログにも秘密が残らない**（罠 #55 の根本対策）

### 6-2. ポータルの既存ログインの再利用

- 再利用できる: ログイン画面（メール＋パスワード・bcrypt）、`getSessionUser()`、ユーザーの `role`・`status`
- **そのままでは不十分な点**: セッション Cookie `bs_session` の中身が**ユーザーIDそのまま**（署名なし）。ユーザーIDを知られると誰にでもなりすませる。個人単位のデータを外に出す前に、**セッションを署名付き（または DB に保存した乱数トークン）に変えることを先にやる**べき。また SSO 用の署名鍵に固定の既定値がある（`/api/auth/sso-token`・環境変数が無いときに使われる）
- 構成案（自前で作る場合）:
  1. 新しい表 3つ: `oauth_clients`（登録されたクライアント）、`oauth_auth_codes`（PKCE の値・有効10分・1回限り）、`oauth_tokens`（アクセス・リフレッシュトークンは**ハッシュだけ保存**・有効期限・取り消し日時・ユーザー）
  2. 新しい入口: 2つのメタデータ、`/api/oauth/register`、`/oauth/authorize`（未ログインならログイン画面へ→同意画面→コード発行）、`/api/oauth/token`、`/api/oauth/revoke`
  3. MCP の新しい入口 `/api/mcp`（秘密なし）でトークンを確かめ、**使える人を限定**（`role=admin` か、許可リストの社員だけ）。ツールごとに必要な権限（集計のみ／明細）を分ける
  4. 移行期間は秘密URLの入口を残し、OAuth の入口が動いたら秘密URLを止める（`MCP_PATH_SECRET` を消す）
- 作業量の見込み: セッションの強化 1〜2日、OAuth の自前実装 3〜4日、テスト・ChatGPT での接続確認 1〜2日 → **合計 1〜1.5週間**。外部の認証サービス（Auth0・WorkOS など）を使えば OAuth 部分は短くなるが、新しい契約と、社員アカウントの二重管理が増える
- デプロイ区分: **staging 必須**（認証の変更）。ログインの変更は全員に影響するので、営業時間外に入れる

### 6-3. 判断事項（大野さん側）

- **求職者の個人単位のデータ（匿名化したものを含む）を外部の AI（ChatGPT）に渡してよいかは、社内規程と求職者の同意（利用目的の範囲）の確認が要る。これは大野さん側の判断事項。**
