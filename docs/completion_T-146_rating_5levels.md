# T-146 完了報告｜ブックマーク評価の5段階化（A / B+ / B / C / D）＋ 評価内訳の表示

最終更新: 2026-07-29（JST）
前提調査: `survey_T-146_rating_5levels_phase1.md`（Phase 1）
状態: **Phase 2 完了・master 反映済み**

---

## 0. 何が変わったか（3行）

1. 総合評価が **A / B+ / B / C / D の5段階**になった。良い順は `A > B+ > B > C > D`。**本人希望・通過率の2軸は A/B/C/D の4段階のまま**（B+ は総合のみ）
2. AIが `総合A〜B` のような**幅のある評価を返す設計を廃止**した。総合評価テーブルは希望×通過の**全16通りを単一値で網羅**する
3. ブックマークタブに**評価内訳**（総数＋総合の構成比）を表示するようにした

---

## 1. 発端と原因

課題は「`B〜C` のような幅を持った評価が増えている」だった。Phase 1 の調査で、**AIの暴走ではなくこちらがそう指示していた**ことが判明した。

`src/skills/job-matching-advisor/SKILL.md` の総合評価テーブルが、7行中5行で幅の値を返す設計になっていた。

```
| A × B    | 総合A〜B  |  ← 幅
| B × A    | 総合A〜B  |  ← 幅
| A × C〜D | 総合B〜C  |  ← 幅
| C × A〜B | 総合B〜C  |  ← 幅
| D × 任意 | 総合C〜D  |  ← 幅
```

発生日は **2026-07-17**（コミット `0a5138c` でスキルを判定用/フル版に分離した日）。4〜6月は幅評価 0 件、7/17 以降は 25〜34% で高止まりしていた。

## 2. 総合評価テーブル（確定版）

希望×通過の **16通りすべてを網羅**し、表にない組み合わせを存在させない。

| 希望 × 通過 | 総合評価 |
|---|---|
| A × A | 総合A |
| A × B | 総合B+ |
| B × A | 総合B+ |
| A × C〜D | 総合B |
| B × B | 総合B |
| B × C | 総合C |
| B × D | 総合C |
| C × A〜B | 総合C |
| C × C | 総合C |
| C × D | 総合D |
| D × 任意 | 総合D |

被覆: 希望A(4) + 希望B(4) + 希望C(4) + 希望D(4) = **16/16**、重複なし。

**設計思想**: 総合評価は「本人の希望に合っているか」を優先して決める。希望に合わない求人は選考を通過しやすくても本人が応募しないため、良い評価を付けても紹介に結びつかない。したがって希望Aは通過が厳しくてもBを維持し、希望Cは通過が堅くてもCに留める。

**B+ の位置づけ**: 希望と通過のどちらか一方がA、もう一方がBの層。紹介する価値は明確にあるが最優先ではない。必須要件未充足（通過率D）の求人が総合A・総合B+ になることはない。

**B- は作らない**（下位側は C との弁別が実データで確認できていないため）。

### B+ 新設の根拠（2026-07-28 の実データ）

- 通過率ランクは **B が 49.4%** を占め、判定が集中していた
- とくに **希望B × 通過A の 580 件**は総合が **A 54% / B 41%** に割れており、中間段階の欠如が原因と判断した

## 4. ★既存データの扱い（重要）

本番DBに **幅表記のデータが 169 件残っている**（総合164 / 通過率4 / 本人希望2）。**再判定しない方針。**

読み取りは**従来どおり先頭1文字**を返す。

| 生テキスト | 読み取り結果 |
|---|---|
| `B〜C` | `B`（**`B+` と誤読しない**） |
| `A〜B` | `A` |
| `B+` | `B+` |

これを保証するため、交替は必ず **`B\+` を先に試す順序**とする。`[ABCD]\+?` のような書き方は `A+`/`C+` まで拾うので**禁止**。

実データ 6,263 件で旧実装と新実装を突き合わせ、**読み取り値の差分 0 件**を確認済み。

### 4-1. 併せて直した既存バグ

幅表記の行が `RATING_LINE_RE` で `■ 総合：B` までしか除去されず、**`〜C` がマイページの本人向けコメント冒頭に残っていた**（該当169件すべてで発生）。

```
修正前: 【ABホテル株式会社】ホテルスタッフ\n〜C\n\n寺澤さんが医療現場で…
修正後: 【ABホテル株式会社】ホテルスタッフ◆未経験でも支配人など…
```

除去専用の `RATING_VALUE_WITH_RANGE` を追加し、**除去側だけ**幅表記の末尾まで飲み込むようにした。読み取り側は不変。

## 5. 踏んだ罠・今後のための注意

1. **モジュールキャッシュ**: `load-job-matching-skill.ts` がスキルをプロセス内にキャッシュする。SKILL.md を直しても**再デプロイしないと反映されない**。「直したのに効かない」ときはまずデプロイ完了を疑う
2. **既存データは全て A/B/C/D なのでテストが全部通る**: コード側だけ5段階にしても既存テストは緑のまま。B+ が1件も生成されないことにリリース後まで気付けない。**必ず新規にAI分析を実行して確認する**
3. **幅評価は画面上ほぼ不可視**: バッジは先頭1文字しか表示しないため、本文が `B〜C` でも画面は `B` に見える。確認は必ず `aiAnalysisComment` の生テキストで行う
4. **`+` は正規表現のメタ文字**: エスケープ漏れが全パース箇所で起こりうる
5. **行末 `$` アンカー付きの正規表現**（`markerLineRe`）は機械置換では直らない。`[ABCD]?\s*$` は `B+` にマッチせず、既存行を検出できないまま**新しい行を挿入して評価行が2重化**する
6. **`toMatchLabel` の3重コピー**: `default: return ""` に落ちるため例外もログも出ず、1箇所だけ直すと「個別編集では出るが一括同期でだけ消える」再現困難な不具合になる → 共通化済み
7. **`DailyReportView` の同名定数の取り違え**: `RANK_ORDER`（求職者ランク・触るな）と `RATING_ORDER`（AI評価・直す）が同一ファイルに同居している
8. **3世代のデータが同一カラムに混在**: 〜7/16 は A/B/C/D、7/17〜7/28 は幅混在、以降は5段階。ランク別集計は章を分けること（`SKILL_full.md` の検証履歴年表を参照）

## 6. B+ の発火について

大野テスト（5999999）で3回 AI分析を実行したが、**発火条件の `希望A × 通過B` / `希望B × 通過A` が一度も出現せず**、AI経由での B+ 生成は確認できていない（この求職者は 38歳・高卒・希望勤務地が神奈川/東京という条件で、通過率が C/D に寄るため）。

代わりに **CA手動編集（3軸セレクトで総合を B+ に変更）** で全経路を検証した。保存は `PATCH /files/[fileId]` を通るため、`aiMatchRating` の保存・マーカー行の置換・`comment-split`・`toMatchLabel`・バッジ・ソートすべてが AI 生成時と同一経路になる。

なお AI 自身は B+ をランクとして認識しており、総合まとめに「総合A・**総合B+**は該当なし」と出力している。
