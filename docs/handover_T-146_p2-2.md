## 1. P2-1 で確定した総合評価テーブル（16通り網羅版・全11行）

出典: `src/skills/job-matching-advisor/SKILL.md` L448-462（`SKILL_full.md` および `analyze-batch` の `EVAL_RULES` にも同一内容を反映済み・3箇所同期）

総合は **A / B+ / B / C / D の5段階**、良い順に **A > B+ > B > C > D**（B+ は A と B の間）。

| 希望 × 通過 | 総合評価 |
|---|---|
| A × A | 総合A |
| A × B | 総合B+ |
| B × A | 総合B+ |
| A × C〜D | 総合B |
| B × B | 総合B |
| B × C | 総合C |
| B × D | 総合C |
| C × A〜B | 総合C |
| C × C | 総合C |
| C × D | 総合D |
| D × 任意 | 総合D |

> **本表は希望×通過の全組み合わせを網羅する。表にない組み合わせは存在しないため、AIが独自に判断してはならない。**

被覆: 希望A(4) + 希望B(4) + 希望C(4) + 希望D(4) = **16/16、重複なし**。
（`A × C〜D` は2通り、`C × A〜B` は2通り、`D × 任意` は4通りを表す圧縮行）

補足で確定済みの仕様:
- **B+ は総合のみに存在。** 本人希望適合度・選考通過率の2軸は A/B/C/D の4段階を維持（SKILL.md L413 に明記）。
- **範囲表記・曖昧表現は明示的に禁止。**「A〜B」「B〜C」等の範囲、「Bより」「B寄り」「Bに近いC」等は使用しない（SKILL.md L468）。
- 設計思想: 総合は「本人の希望に合っているか」を優先。希望Aは通過が厳しくてもBを維持し、希望Cは通過が堅くてもCに留める。
- 必須要件未充足（通過率D）の求人が総合A・総合B+ になることはない。

## 3. 既存データに幅表記が残っている件（要検証）

- **本番DBで幅表記を含む `candidate_files` は 168 件**（2026-07-28 実測。`ai_analysis_comment ~ '(本人希望|通過率|総合)[：:] *[ABCD] *[〜~ー-] *[ABCD]'`）。
  ※ Phase1 調査書では 146 件と記載。**その後増えて 168 件**になっている（P2-1 で AI 側を止めるまで発生し続けていたため）。
- 方針は**再判定しない**（AI費用がかかるため）。したがって `■ 総合：B〜C` のような行はDBに残り続ける。
- **必須の検証**: B+ 対応でパーサを触ったとき、**`B〜C` が誤って `B+` と解釈されないこと**。
  - 危険なパターン: `/(B\+|[ABCD])/` は `B〜C` の先頭 `B` を拾う（＝従来どおり B）。ここは変わらないはずだが、
    `[ABCD]\+?` や `[ABCD][〜~]?[ABCD]?` のような**欲張りな書き方をすると挙動が変わる**。
  - 特に `〜` の直後に `+` が来る文字列は存在しないが、全角チルダ・波ダッシュ・長音符・ハイフンの表記ゆれ（`〜 ~ ー -`）が混在している点に注意。
- 現状の `ai_match_rating` の実値分布（2026-07-28 実測）: **B 2322 / A 1796 / C 1587 / D 581 — B+ は 0 件**。
  つまり**B+ が1件でも入ったら P2-1 が効いた証拠**であり、逆に0件のままならリリース後も効いていない。
- 3世代（過去=A/B/C/D のみ → 7/17〜=幅混在 → B+ 導入後=5段階）が同一カラムに混在するため、**集計の見せ方には注釈が必須**（地雷#8）。

## 4. 動作確認の制約（重要）

- **大野テスト（5999999）では B+ が発火しない。** 実測で確認済み:
  同求職者のブックマーク63件の 希望×通過 の組み合わせは
  `D×D:9 / B×B:8 / B×C:6 / D×C:6 / C×D:4 / B×D:2 / C×B:2 / C×C:1 / A×D:1 / D×B:1` の10通りで、
  **B+ の発火条件である `A×B` と `B×A` が1件も存在しない**。
  → テストユーザーで analyze-batch を回しても B+ は出ない。**「出ないから壊れている」と誤判断しないこと。**
- **検証環境（staging）と本番は同一の PostgreSQL を共有している。**
  したがって **他の求職者で analyze-batch を実行することは絶対に不可**（本番データを書き換えてしまう）。
- 現実的な検証手段:
  1. **パーサ／表示／ソートは単体で B+ 文字列を流し込んで確認**する（DBを経由しない。P2-2 の検証方法として調査書 L489 が指定）。
  2. B+ の実発火を見たい場合は、A×B が成立する求人票を**テストユーザー配下に新規で用意**してから回す。
  3. SKILL.md は `load-job-matching-skill.ts` の `cachedSkill` がプロセス再起動まで保持されるため、
     **staging で「直したのに反映されない」ように見える。再デプロイ必須**（地雷#2）。
