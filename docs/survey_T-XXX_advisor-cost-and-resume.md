## 結論

1. チャット1往復は直近30日で **平均 ¥24.2（中央値 ¥25.6・最大 ¥51.9）**。ほぼ Sonnet 4.6 単価の実績で、同じトークン数を Sonnet 5 単価（本日 13:51 に切り替え済み）で計算し直すと **平均 ¥16.2**。AIアドバイザー系の帳簿（AdvisorUsageLog）は直近30日で合計 ¥33,886。うちチャットは ¥3,965 で、73% は求人全件分析（¥24,712）。
2. 1往復の入力は約4.5万トークン。うち約2.5万は**毎回送る固定部**（人物設定＋SKILL_full＋タスク検出指示、2.8万字）。キャッシュ読みが効いた呼び出しは25%しかない。会話が1往復で終わることが多く、5分キャッシュがほぼ毎回切れているため。
3. **書類の AI 読み取りは往復ごとには走らない**。一度読み取った結果（parsedText）を保存して使い回しており、走るのは未読の書類があるときだけ（Gemini・1回約 ¥1.1、AiUsageLog に記録）。応答は**ストリーミングではなく**、全文を待ってから表示する（通常の質問で平均25秒、タイプ診断で88秒）。
4. マイナビレジュメは **Google Drive**（求職者ごとのフォルダ）に `CandidateFile` の **category=MEETING**（面談タブ）として保存される。直近3ヶ月に登録された「マイナビ転職」の求職者のうち **86.0%** が RPA 取り込みのPDFを持っている。取り込み時に Gemini が抽出するのは氏名・連絡先・希望条件だけで、**本文テキストは保存していない**。
5. 既存の `pdf-parse` を使えば、**AIを使わずに文字を取り出せる**（5件すべてで学歴・職歴の見出しが取れた。本文はおよそ500〜2,400字）。試算Bでは求職者1人あたり（整理1回＋質問10往復）が **約 ¥50〜67**（現行方式Aは約 ¥72〜203）。B でも費用の大半は「履歴の送り直し＋出力」が占める。

`getCandidateContext()`（`src/lib/advisor-context.ts`、mode="chat"）が集める項目:
基本情報（氏名・番号・メール・生年月日・性別・担当CA・登録日）／面談ログの要約（`advisorLogDigest`）／転職軸ワークシート／PREP シート／AI自己分析レポート／職務経歴書の解析テキスト（ガイドの `parsed_resume`）／CAメモ全件／ファイル一覧／**主要書類の本文**（ORIGINAL・BS_DOCUMENT・MEETING の PDF/txt の新しい順4件。面談 txt は1件8,000字まで。要約がある人は面談 txt を除く）／応募履歴20件／ブックマークの評価一覧／ブックマーク求人票の最新5件（1件1,500字）

**書類の AI 読み取り（罠#39 の観点）**
- **往復ごとには走らない**。チャット側も T-164 で対応済み。(1) 候補者情報はセッションごとに `contextCache` に保存し、材料の指紋（`contextFingerprint`）が一致する間は再利用する（上限24時間）。(2) 作り直す場合も、書類本文は `CandidateFile.parsedText` に保存済みならそれを使う。Gemini（`parsePdfWithAI`）が走るのは parsedText が空の書類だけで、失敗した場合は次回また試す。
- その費用は **AiUsageLog**（`file-parse`・caller=`advisor-context`）に入り、AdvisorUsageLog には入らない。1回あたり約 ¥1.1（1-2 の表）。
- 実際には候補者情報を作り直す往復が約82%ある（翌日以降の再訪で24時間を超える、ファイルが追加される、など）。ただ、作り直しは DB を読むだけのことが多い。

**キャッシュの効き方**
- `cache_control`（5分）は system の2ブロックに付いている。固定部は**全求職者で共通**なので、別の求職者の呼び出しでも読める。履歴と質問には付いていない。
- 直近30日の実績では、キャッシュ読みがあった呼び出しは **41/164（25.0%）**、入力合計に占めるキャッシュ読みは **20.1%**。1往復あたりの書込が平均 28,067 トークンと大きい。前回調査のとおり、会話の83%が1往復で終わり、呼び出し間隔も長いため。**毎回キャッシュを書き込み直している状態が主な費用**になっている。

**応答方式とパラメータ**
- **ストリーミングではない**（`fetch` の後に `response.json()` で全文を待つ。タイムアウトは120秒）。
- モデル: `getChatModel()` = 環境変数 `CHAT_MODEL`（既定 `claude-sonnet-5`、`src/lib/claude.ts`）。`selectModel()` による Opus への振り分けはコメントアウトされている。
- `max_tokens`: 通常 4,000、面談ログ同梱時 10,000（route 内で指定）。Sonnet 5 では `chatRequestParams()` が1.3倍にする（5,200 / 13,000）。思考は無効、temperature は送らない。

### 3-4. AI を使わずに文字を取り出せるか（実物5件・読み取り専用で Drive から取得）

- ライブラリ: **`pdf-parse`（^1.1.1、導入済み）**。ほかに `pdfjs-dist`（^5.6）もある。今回は追加していない。

### 3-5. レジュメ由来の経歴は DB にあるか

- **レジュメから経歴を構造化して保存する経路は無い**。`WorkHistory`（職歴）と `InterviewDetail.educationFlag/Memo`（学歴）は**面談記録（InterviewRecord）に付く、CA の入力欄**。
- 直近3ヶ月のマイナビ転職登録者（465人）の充足率: 面談記録あり 55.5%／職歴あり 41.3%／学歴あり 41.3%／ガイドの `parsed_resume` あり 0.0%。
- → **面談前の時点では、経歴は Drive の PDF の中にしか無い**。

## 4. 会話の保存構造

| テーブル | 主な列 |
|--|--|
| `advisor_chat_sessions`（`AdvisorChatSession`） | candidateId、title（最初の質問の先頭30字）、**createdByUserId（作成した CA）**、contextCache／contextCachedAt／contextFingerprint（候補者情報のキャッシュ）、createdAt／updatedAt |
| `advisor_chat_messages`（`AdvisorChatMessage`） | sessionId（セッション削除で一緒に消える）、**role（user / assistant。CA 個人の列は無い）**、content、createdAt、suggestedTasks（タスク候補）、kind（`ANALYSIS`＝全件分析のカード） |

- 1人あたりのセッション数に上限は無い。ただ画面は実質1セッションで使われている（現存905セッションのうち877人が1セッション。1セッションのメッセージ数は平均7.9、中央値0、最大111）。
- **使用量ログとメッセージを直接つなぐ列は無い**（AdvisorUsageLog に sessionId も messageId も無い。candidateId と時刻で突き合わせるしかない）。
- **「履歴クリア」はセッションごとの物理削除**（`DELETE /advisor/sessions/[sessionId]` → `advisorChatSession.delete`。メッセージも Cascade で消える）。その直後に空のセッションを新しく作る。非表示にする方式ではなく、元に戻せない。使用量ログは残る。

## 5. 試算（新方式の見込み）

※以下はすべて**試算**。単価は Sonnet 5（コード内の単価表にある値: 入力 $2・出力 $10・キャッシュ読 $0.2・キャッシュ書（5分） $2.5／100万トークン）、1ドル=150円。

| 前提 | A: 現行方式 | B: 新方式 |
|--|--|--|
| 固定の指示 | 24,963 トークン（人物設定＋SKILL_full＋タスク検出） | 3,000 トークン（準備用の短い指示） |
| 求職者の材料 | 候補者情報 12,544 トークン（実測の中央値） | レジュメ本文＋基本情報 2,000 トークン（pdf-parse で1回取り出して保存。実物は500〜2,400字）。**取り出し費用は ¥0**（AI なし） |
| キャッシュ指定 | 上の2つに5分 | 上の2つに5分（合計5,000 トークン。Haiku の最小長4,096 も超える） |
| 履歴 | 直近20件（キャッシュなし） | 直近10往復＝20件（キャッシュなし） |
| 最初の整理 | 質問 300・出力 2,000 トークン | 同じ |
| 追加の質問 | 1回あたり質問 300・出力 1,106 トークン（直近30日の通常の質問の実測平均）。履歴は1往復ごとに約1,400 トークン増える | 同じ |
| キャッシュ命中 | 良い場合: 11回が5分以内に続く／悪い場合: 毎回切れる（実績の命中率は25%） | 同じ |

| 試算 | A（良い場合） | A（悪い場合） | B（良い場合） | B（悪い場合） |
|--|--:|--:|--:|--:|
| 最初の整理（1回目） | ¥17.3 | ¥17.3 | ¥5.0 | ¥5.0 |
| 追加の質問 1往復の平均 | ¥5.5 | ¥18.5 | ¥4.5 | ¥6.2 |
| **求職者1人あたり（整理1回＋質問10往復）** | **¥72** | **¥203** | **¥50** | **¥67** |
| 参考: 今の実績（1往復の平均・Sonnet 5 に換算） | ¥16.2 | | | |

計算の内訳（B・良い場合）: 1回目はキャッシュ書込 5,000×$2.5 ＋ 入力 300×$2 ＋ 出力 2,000×$10 = $0.033。2〜11回目は、キャッシュ読 5,000×$0.2×10回 ＝ $0.010、履歴＋質問の合計 89,270×$2 ＝ $0.179、出力 1,106×$10×10回 ＝ $0.111。合計 $0.332 ＝ ¥50。

- B では、固定部を短くすることで1回目が ¥17→¥5 になり、キャッシュが切れたときの損も小さくなる（A は1回切れるごとに約 ¥13 の書き直し、B は約 ¥1.7）。
- 一方、B の費用の **約55%は履歴（キャッシュなしで毎回送り直す）、約40%は出力**。さらに下げる手段は次のとおり。どれも今回は試算だけ。
  - 履歴を5往復に縮める
  - 過去のやり取りを要約して持つ
  - 履歴の末尾にもキャッシュ指定を付ける（最後の user メッセージに `cache_control` を付けると、10往復が続けて行われる場合は履歴の大半が読み扱いになる）
- 月額の目安（試算）: 新人CA1人が月30人を準備すると、B で ¥1,500〜2,000。1人あたり月 ¥3,000 のサブスクと同額になるのは、B で**月45〜60人**（A だと15〜40人）。
