## 0. エグゼクティブサマリ

### 0-1. 症状は再現・原因は確定

ファイル名に会社名以外の文字（括弧書き・キャッチコピー・記号）が混ざると、`extractSearchNames()` が**その不純物ごと**を検索名として返す。AI出力の見出しは `【会社名】` の形なので、`【[^】]*検索名[^】]*】` は**永久にマッチしない**。結果 Phase2 がセクションを取り出せず、`skipping partial save` で**コメントも評価も保存されない**。

一覧の評価列が空欄のままになるのはこのため。

## 1. 調査項目1: 現在の切り出しロジック

### 1-1. `extractSearchNames()`（`analyze-batch/route.ts` L210-253）

ファイル名から**検索名の候補配列**を作る。候補は順に試され、**最初にマッチしたものでセクションが確定**する。

| # | パターン | 対応形式 |
|--|--|--|
| p1 | `^求人票[_]?(.+?)(?:_\d{10,})?$` | `求人票_会社名_20260413194430596.pdf` |
| p2 | `^\d+[_](.+?)(?:_\d{10,})?$` | `32893_会社名.pdf` |
| p3 | `^(.+?)_No\d+$` | `会社名_No123.pdf` |
| pBee | `^(.+?)[：:]\d+$` | `会社名：141427.pdf`（Bee形式・コミット `15cd745` で追加） |
| p4 | `^求人票[_]?(.+)$` | 上記に当てはまらない求人票_ 形式 |
| — | 該当なし | ファイル名そのまま |

さらに各候補について「法人格を除去した版」と「全角英数→半角版」を追加する。

**★ここが本件の核心★** — 上記はいずれも**先頭の接頭辞と末尾の数値ID／拡張子しか落とさない**。`（…）`、`【…】`、`、`、`／`、`※`、キャッチコピーは**一切除去されない**。

### 1-2. 照合側（同ファイル L103-140）

```
【[^】]*${検索名}[^】]*】        ← 検索名が 】 を跨げない
```

検索名に `【` `】` が含まれる、あるいは AI が出力する会社名見出しに含まれない文字列（括弧書きの説明文等）が含まれると、**構造上マッチ不能**。

失敗時は `results` に追加せず警告のみ:

```
[AnalyzeBatch] Phase2 failed to extract section, skipping partial save: fileId=..., fileName="...", searchNames=[...]
```

**部分保存を避ける安全設計**だが、その結果ユーザーには「AI分析したのに空欄」としか見えない。

### 1-3. 各正規化関数が何を落とすか

| 関数 | 置き場所 | 落とすもの | 落とさないもの |
|---|---|---|---|
| `stripFileMetadata()` | `lib/normalize-filename.ts` | `.pdf` / 先頭 `求人票_` / 先頭 `数字_` / 末尾 `_\d{10,}` / 末尾 `：数字` / 末尾 `_No\d+` | **括弧書き・読点・記号・キャッチコピー** |
| `stripCorpSuffixes()` | 同 | 株式会社・有限会社・合同会社・各種法人 | 同上 |
| `normalizePortalFileName()` | `restore-jobs/route.ts` | `stripFileMetadata` と同一 | 同上 |
| `normalizeKyuujinCompanyName()` | `restore-jobs` / `job-introductions` | 末尾 `_\d{14,}` / 末尾 `：数字` | 同上 |
| `normalizeCompanyName()` | `analyze-batch` 内 | 法人格・全角英数・`・`・空白（＋小文字化） | 同上 |

**どの関数も括弧書き以降を落とさない。** これが全パターンに共通する根本原因。

### 1-4. ★重要★ 影響経路は analyze-batch に閉じている

```
extractSearchNames  → analyze-batch/route.ts L81・L103 のみ（他に使用箇所なし）
stripFileMetadata   → restore-jobs / to-entry / job-introductions / extraction-complete /
                      candidate-site-notifications / HistoryTab
```

**`extractSearchNames()` を直しても、マイページ送信・求人紹介への移動・kyuujinPDF との会社名マッチングには一切影響しない**（それらは `stripFileMetadata` 系の別経路）。修正の影響範囲は極めて限定的。

### 3-2. 修正方針（正規表現の追加案）

**方針: 既存の候補配列は一切変えず、末尾に「会社名コア」候補を追加するだけにする。**
候補は先頭から順に試され最初の一致で確定するため、**現在成功している照合は今までどおり先に確定する＝デグレしない。**

```ts
const LEGAL = "株式会社|有限会社|合同会社|合資会社|一般財団法人|公益財団法人|一般社団法人"
            + "|医療法人社団|医療法人|学校法人|社会福祉法人|特定非営利活動法人|独立行政法人|国立大学法人";

// R0: 末尾の _No12345_ / 全角空白 にも対応（P7・P8）
const stripTrailingNo = (s: string) => s.replace(/_No\d+_?$/i, "").trim();

// R1: 法人格が後置なら、その直後で切る（P1・P2・P3・P6）
function cutAfterLegalSuffix(s: string): string | null {
  const m = s.match(new RegExp(`^(.{1,40}?(?:${LEGAL}))`));
  return m && m[1].length < s.length ? m[1] : null;
}

// R2: 会社名に通常現れない区切り以降を落とす（P4・P5・P9）
const DELIM = /[_＿（(【《〔\[、／/|｜※＼★◆♦☆▼●〇■□〜~]|\s\-\s/;
function cutAtDelimiter(s: string): string | null {
  const m = s.match(DELIM);
  return m && m.index !== undefined && m.index >= 2 ? s.slice(0, m.index).trim() : null;
}
```

`extractSearchNames()` の `return expanded;` の直前で、`cutAfterLegalSuffix` → `cutAtDelimiter` → 素の seed の順に候補を**末尾へ**追加し、それぞれの法人格除去版も足す。

| **短い会社名の誤マッチ** | `株式会社ABC` が `【株式会社ABCデザイン】` に一致しうる | **既存の法人格除去版でも同じリスクが既にある**。候補を末尾に足す方式なので新規リスクの増分は小さいが、同一バッチに類似社名がある場合は誤マッチの可能性が残る |
| **別原因の470件** | §4 参照 | 本修正では救えない |

## 4. 調査項目4: 「AI評価対象外10件」との関係 → **別原因**

大野テスト（5999999）の内訳:

- BOOKMARK 総数 62（アクティブ52 ＋ 紹介保留10）
- 「AI評価対象外」の条件（`origin="candidate"` かつ `driveFileId=null` かつコメント無し）に該当: **18件**（うちアクティブ **10件** ＝ 画面表示と一致）
- **18件すべてが `extractedAt` も無し**

```
求人票_パーソルビジネスプロセスデザイン株式会社.pdf   extractedAt=無 origin=candidate
求人票_株式会社dinos.pdf                              extractedAt=無 origin=candidate
求人票_28251_株式会社ヨコオ.pdf                       extractedAt=無 origin=candidate
…
```

ファイル名自体は素直で、切り出しは正常に動く。**PDF実体が無くテキスト抽出されていないため、そもそもAI分析の対象に入らない**（`AdvisorFloatingPanel` が `extractedAt` ありのファイルだけを対象にする）。

→ **本件（会社名切り出し）とは無関係。仕様どおりの表示であり、修正対象ではない。**

## 5. 調査項目5: 影響範囲と再判定

### 5-1. 影響範囲

| 区分 | 件数 | 求職者数 |
|---|--:|--:|
| スキップ疑い 全体 | 575 | 121名 |
| **うち本件（ファイル名の不純物）** | **105** | **52名** |
| うち別原因 | 470 | 96名 |

### 5-2. 別原因470件の性質（本件とは切り離すべき）

| 内訳 | 件数 |
|---|--:|
| 1名あたり5件以上まとまってスキップ（**バッチ単位の失敗の疑い**） | 360 |
| 散発（1名あたり4件以下） | 110 |
| その求職者で成功が0件（一度も保存できていない） | 26 |

上位は `スキップ48/BM58`、`スキップ26/BM26（成功0）` のように**まとまって落ちて**おり、会社名の切り出し失敗（個別ファイル単位で起きる）とは分布が異なる。**バッチ自体の失敗（レート制限・タイムアウト・AIが一部求人を出力しない）** が主因と推測される。別チケットでの調査を推奨。

### 5-3. 再判定のコスト

修正後、既存の失敗分を救うには**再判定が必要**（修正は切り出しロジックのみで、過去の欠落データは自動では埋まらない）。

| 対象 | 件数 | バッチ数（5件/バッチ） |
|---|--:|--:|
| 本件で救える見込み | 105 | 約 21 |
| スキップ疑い 全件 | 575 | 約 115 |

**推奨: まず 105 件（約21バッチ）だけを対象に再判定する。** 別原因の470件を含めると5倍以上のコストがかかるうえ、原因未特定のまま再実行しても同じ理由で再び失敗する可能性が高い。

再判定は AdvisorFloatingPanel の **「未評価/破損のみ」モード**で求職者ごとに実行できるが、52名にまたがるため運用負荷がある。スクリプト化する場合は対象 fileId を明示的に絞ること。

## 6. 結論

1. **原因は確定。** `extractSearchNames()` が括弧書き・キャッチコピー・記号を除去しないため、AI出力の `【会社名】` と構造上マッチできない
2. **修正方針は「候補を末尾に追加するだけ」。** 実データで **+100件が照合可能**になり、**現在成功している 6,263 件の候補順序は 1 件も変わらない**
3. **影響範囲は analyze-batch に閉じている。** `extractSearchNames` は他から呼ばれておらず、マイページ送信・kyuujinPDF の会社名マッチングは `stripFileMetadata` 系の別経路のため**影響しない**
4. **「AI評価対象外10件」は別原因**（PDF未保管・テキスト未抽出）で、修正対象ではない
5. **残る470件は別問題**（バッチ単位の失敗の疑い）。本件の修正では救えず、別途調査が必要
6. 再判定は本件分の **105件（約21バッチ）**に絞ることを推奨
